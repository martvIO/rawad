1. After login, the user is not redirected to the dashboard ("spinner hangs forever").

evidence gathered, the diagnosis for each symptom, and the fixes shipped.

## Phase C — Per-symptom diagnosis

### Symptom 1: "After login, the user is not redirected to the dashboard"

**Code path** ([usePortalState.js:378-402](../src/hooks/usePortalState.js#L378)):

```js
setLoginLoading(true);
try {
  const user = await signIn(u, p);
  setAuthUser(user);
  setAuthReady(true);
  setAuthKey((k) => k + 1);
  navigate("/portal/{role}/...", { replace: true });
} catch { setLoginError(t("login_error")); }
finally { setLoginLoading(false); }
```

`signIn` POSTs `/api/auth/login`, stores tokens, returns the user. With
React 18 batching, all state setters + `navigate` apply in one render.
`PortalRouter` sees `authed = true` and matches the role route.

**Diagnosis:** No active bug in code as of today's deployed bundle. This
behavior was almost certainly broken **before** commit `fdf992f` (which
landed today at 13:30 local). The `/debug` ticket likely reflects pre-fix
observations from earlier today.

**Risk that remains:** if the network truly stalls (very rare; cold-start
+ flaky mobile combination), `signIn` could hang for the full default
fetch timeout (browser-dependent, typically minutes), with the spinner
stuck. **Fixed defensively** — see below.

### Symptom 2: "Overall website logic broken"

Open-ended. After reading the routing, state, and DB layers:
- Routing is URL-driven and correct (NavLink + nested Routes for tabs in
  admin/driver/groom portals).
- State is monolithic (one big `usePortalState` exposed via context) but
  not broken — 404 unit tests pass.
- No memory-leak patterns: every `useEffect` returns a cleanup; pollers
  return `unsubscribe()` consistently.

**Diagnosis:** Not a specific bug. The complaint is symptomatic of the
other two issues (login + uploads). Once those are resolved the
"everything's broken" feeling should subside.

### Symptom 3: "DigitalAddGuest form hangs"

**Code path** ([DigitalAddGuest.jsx:39-65](../src/pages/portal/groom/digital/DigitalAddGuest.jsx#L39)):

```js
setSaving(true);
try {
  const id = await addDigitalGuest(currentUid, {...});
  navigate("/portal/groom/digital/guests", {...});
} catch {...}
finally { setSaving(false); }
```

`addDigitalGuest` is a `POST /api/digital/{uid}/guests`. If the network
returns 401/403/400 or throws, the `finally` clears the spinner and the
catch shows a toast — so the form should always recover.

The hang scenarios:
- **The request literally never resolves** (network black hole / cold-start
  beyond the browser's tolerance). No frontend timeout was set.
- **`navigate` fires successfully but the component unmounts before
  `finally`** — the `setSaving(false)` then runs on a dead component
  (React warning, no actual hang).
- **`currentUid` is `null`** when submit fires (auth still resolving) — call
  proxies through `getStoredUid()` which IS set at that point, so this is
  unlikely but possible.

**Diagnosis:** No deterministic bug, but defensive hardening warranted —
see fixes below.

### Symptom 4: "Photo upload stays uploading… forever"

**Code path** ([DigitalDashboard.jsx:79-103](../src/pages/portal/groom/digital/DigitalDashboard.jsx#L79)):

```js
setBusy(true);
const results = await Promise.allSettled(files.map(f => addInvitationMedia(uid, f)));
setBusy(false);  // always runs
previews.forEach(p => { if (in succeededIds || failedIds) revoke });
setPendingMedia(...);
```

`Promise.allSettled` always resolves once every input promise settles, so
`busy` always clears. But `addInvitationMedia` is `api.upload(...)` —
which calls `fetch` with no timeout. **If a single upload's fetch never
resolves, the `Promise.allSettled` never settles, and `busy` + the
pending "⏳" tile stay forever.**

**Diagnosis:** This *is* a real bug. The `api.upload` path had no timeout
and no way to abort on component unmount.

## Fixes shipped

### Fix 1: `fetchWithTimeout` in apiClient

[src/utils/apiClient.js](../src/utils/apiClient.js) — wrapped every
`fetch` call (both `request` and `upload` paths, including the 401-retry)
in an `AbortController`-backed timeout helper:

- 30s default for JSON requests ([API_TIMEOUT_MS.DEFAULT](../src/config/index.js)).
- 2 minutes for uploads ([API_TIMEOUT_MS.UPLOAD](../src/config/index.js)).
- Timeout throws `Error("request_timeout")` — distinguishable from
  `network_error`.
- Caller-supplied `AbortSignal` is honored on uploads (passed via `opts.signal`).
- Original error logging preserved via `logErr`.

This ensures **no fetch can hang the spinner forever**, regardless of
network or backend behavior.

### Fix 2: AbortController on digital uploads

[DigitalDashboard.jsx](../src/pages/portal/groom/digital/DigitalDashboard.jsx)
and [DigitalPhotographer.jsx](../src/pages/portal/groom/digital/DigitalPhotographer.jsx):

- Track an `AbortController` ref per page.
- Pass `{ signal: controller.signal }` to every `addInvitationMedia` /
  `uploadPhotographerFile`.
- On unmount, abort all in-flight uploads.
- Always revoke blob URLs and clear `pendingMedia` after `Promise.allSettled`,
  not just for items the heuristic thinks succeeded — this prevents the
  "⏳" tile from being stranded if the success/failure assignment is wrong.
- Surface `request_timeout` and `AbortError` distinctly: timeouts toast a
  bilingual "retry" message; aborts (user navigated away) toast nothing.

[src/services/digitalInvitation.js](../src/services/digitalInvitation.js):

- `addInvitationMedia(uid, file, opts?)` and
  `uploadPhotographerFile(uid, file, opts?)` now forward `opts` to
  `api.upload`. Existing callers are unaffected (`opts` is optional).

### Fix 3: Guard DigitalAddGuest on `currentUid`

[DigitalAddGuest.jsx](../src/pages/portal/groom/digital/DigitalAddGuest.jsx):

- Submit button disabled when `!currentUid` (prevents racing against auth).
- Submit refuses without `currentUid` and shows a "please reload" toast.
- `setSaving(false)` in `finally` is guarded by a `mountedRef` so it
  doesn't fire on a unmounted component after the optimistic navigate.
- Timeout-aware toast: "انتهت مهلة الطلب — حاول مرة أخرى" / "פג זמן הבקשה — נסה שוב".

### Fix 4: Documentation rewritten

The two `CLAUDE.md` files described the **pre-migration Firebase SDK
architecture** even though the codebase has been REST-only since commit
`fed9d38`. This was actively misleading — even AI agents I dispatched
hallucinated "Firebase SDK race conditions" that don't exist in the
current code.

Both files rewritten:
- [CLAUDE.md](../CLAUDE.md) — Architecture reference (REST flow, three
  critical frontend modules, security model, file layout).
- [.claude/CLAUDE.md](../.claude/CLAUDE.md) — Progress log (recent

New companion docs:

## What we explicitly did NOT do

- **No full rewrite.** The user originally asked for one. The audit
  showed the REST-based architecture is solid (404 unit tests pass,
  backend is well-structured). A rewrite would have discarded working
  code and likely re-introduced the very bugs that today's commits just
  fixed.
- **No deploy.** Pushing to production is the user's call; the fixes are
  ready to ship.
- **No `firebase.js` / `re.js` cleanup.** Both are dead code but removing
  them was out of scope; called out in `.claude/CLAUDE.md` as a future
  task.
- **No splitting `usePortalState`.** It's monolithic (~1000 LOC, 100+
  state vars) and forces some re-renders, but it's not broken. Splitting
  is a refactor, not a fix.
