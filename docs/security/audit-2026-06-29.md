# Security Audit — دعوة (Dawa)

**Date:** 2026-06-29
**Auditor:** Claude (Claude Code) — manual review + automated scanners
**Commit range:** full history (662 commits) + current working tree on `feat/arch-tech-debt-seams`

## Scope & method

Audit focused on the three risk classes most often introduced by AI-assisted code generation:

1. **Hardcoded secrets** — API keys, DB passwords, crypto keys pasted into source / committed to VCS.
2. **Injection flaws** — SQLi (string-concatenated queries), XSS (unescaped user input).
3. **Insecure authentication & crypto** — unverified JWTs, plaintext/weak password hashing, deprecated algorithms, static IVs, non-CSPRNG tokens.

**Method:**
- Manual code review across `frontend/`, `backend/functions/`, `loadtest/`, `scripts/`, infra config (3 parallel review passes).
- **gitleaks 8.30.1** — full git history (662 commits, 35.98 MB) **and** working-tree (`dir`) scan.
- **npm audit** — `frontend/` and `backend/functions/` (prod + dev).
- **Semgrep 1.168.0 SAST** — `frontend/src` + `backend/functions/src`, 114 rules from `p/owasp-top-ten`, `p/javascript`, `p/typescript`, `p/secrets` over 323 files. **Result: 0 findings.**
- **pip-audit 2.10.1** — `loadtest/requirements.txt`. **Result: 0 known vulnerabilities.**

## Executive summary

**The codebase is fundamentally sound on all three focus areas.** No real secret has ever been committed to git history, there are no injection or XSS sinks, and the authentication/crypto implementation is strong (Firebase Admin token verification, RSA-OAEP-SHA256, CSPRNG tokens, timing-safe comparisons, default-deny security rules).

The actionable findings are **not** AI-introduced vulnerabilities in app logic — they are **dependency vulnerabilities** (transitive, fixes available) and **secret-hygiene / tooling gaps** (rotate one chat-shared key, remove a leftover local key, de-hardcode a path, and add a gitleaks allowlist so the existing CI secret-gate is reliable).

## Findings (detail)

### F-1 — Dependency vulnerabilities (High)

`npm audit` reports **21 vulnerabilities in `frontend/`** (18 moderate, 2 high, 1 critical) and **21 in `backend/functions/`** (19 moderate, 2 high). All are **transitive** (pulled by `@aws-sdk/*`, `firebase-admin`, `vite`, `@sentry/*`), not direct dependencies, and most are DoS-class. Notable high/critical advisories:

| Package | Severity | Class | Path |
|---|---|---|---|
| `fast-xml-parser` | **Critical** | DoS / entity-expansion / regex injection / CDATA injection | both (via `@aws-sdk` / firebase grpc chain) |
| `undici` | High | TLS-validation bypass, header injection, cache disclosure | both (firebase-admin / node-fetch) |
| `form-data` | High | CRLF injection via unescaped multipart field names | `backend/functions` |
| `protobufjs` | High | DoS via unbounded Any expansion; property shadowing | `backend/functions` (grpc) |
| `vite` / `esbuild` | High | Path traversal, `server.fs.deny` bypass (dev-server only) | `frontend` (devDependency) |

**Remediation outcome (applied 2026-06-29):**

- **Backend `functions/` — FIXED: 21 → 0 vulnerabilities.** `npm audit fix --force` bumped `@sentry/node` v8 → v10 (the only major change; usage is just `init` + `captureException`, stable across majors) and patched `form-data`/`protobufjs`/`undici`. `npm install` resolves cleanly, `tsc` build passes, and all 440 backend unit tests pass.
- **Frontend `frontend/` — DEFERRED (reverted to committed state).** Forcing the bumps does **not** fix the production-relevant advisories and **destabilizes the toolchain**:
  - The fixable advisories are **dev-only** (`vite`/`esbuild` — build-time dev server, never in the deployed bundle).
  - `--force` bumped `vite` v5 → v8, which **breaks `npm install`** (`@vitejs/plugin-react@4` peer-requires vite ≤ ^7). Pinning vite ^7 installs but **breaks the JSX test runtime** (21 RTL tests fail with `React is not defined`).
  - The **critical `fast-xml-parser`** and the 17 moderate `@aws-sdk/*` advisories are **Amplify-pinned** (`aws-amplify` bundles an old `@aws-sdk/core`). An `overrides` pin to `fast-xml-parser@^5.9.3` triggers an ERESOLVE conflict; clearing them requires an `aws-amplify` major upgrade, which risks the Face-Liveness feature.
  - **Real-world exploitability of the frontend critical is low:** `fast-xml-parser` parses **trusted AWS API responses over TLS**, not attacker-controlled input.
  - → Reverted `frontend/package.json` + lockfile to the known-good vite-5 state (500 tests pass). Tracked for a **dedicated, tested `aws-amplify` upgrade PR** rather than a `--force` that ships breakage.

### F-2 — `LEMONSQUEEZY_API_KEY` shared in plaintext chat (Medium)

`backend/functions/.env.local` carries an inline comment: *"Rotate `LEMONSQUEEZY_API_KEY` after testing — it was shared in plaintext chat."* The key is a JWT-format Lemon Squeezy API key. It is **gitignored and was never committed** (confirmed: gitleaks history scan does not flag it). However, a key that transited a plaintext channel must be treated as exposed.

**Recommendation:** rotate the key in the Lemon Squeezy dashboard (**user action — external**), then update the value in `backend/functions/.env*` and the production secret (`firebase functions:config` / Secret Manager). No git action needed.

### F-3 — Leftover `STRIPE_SECRET_KEY` in local `.env` (Low)

`backend/functions/.env` line 1 sets `STRIPE_SECRET_KEY` (a JWT-format value). No code reads `process.env.STRIPE_SECRET_KEY` — Stripe appears only in comments / dormant config (`config/packages.ts`, `services/createGroomAccount.ts`, `analytics/aggregate.ts`, `sentry.ts`); **Lemon Squeezy is the active payment provider**. The file is gitignored and never committed.

**Recommendation:** remove the unused `STRIPE_SECRET_KEY` (and `STRIPE_WEBHOOK_SECRET` if present) from local `.env`, or document why it's retained. Low risk (local, gitignored), but unused secrets are needless exposure surface.

### F-4 — Hardcoded admin-SDK-key paths in tracked config (Low)

`.claude/settings.local.json` (which **is** tracked in git) embeds absolute filesystem paths to the admin-SDK key in PowerShell/Bash command strings, e.g. `C:\Users\martv\...\dawa-aa793-firebase-adminsdk-fbsvc-e42554a05c.json`. This leaks a username and local directory layout — **not** the key itself (the key file remains gitignored).

**Recommendation:** parameterize via `$GOOGLE_APPLICATION_CREDENTIALS` or a repo-relative path so no absolute machine path is committed.

### F-5 — No gitleaks allowlist → noisy/unreliable secret-gate (Low, tooling)

A full-history gitleaks scan surfaces **5 findings, all false positives**:

| File | Rule | Why it's a false positive |
|---|---|---|
| `backend/tests/functions/streamToken.test.ts:9` | generic-api-key | Test fixture: `STREAM_TOKEN_SECRET = "test-secret-at-least-16-chars-long"` |
| `frontend/src/__tests__/utils/passwordCrypto.test.js:130` | generic-api-key | Test fixture: `key: "bm90LWEta2V5"` (base64 for "not-a-key", per inline comment) |
| `re.js:14` (history only; file deleted in `ac7d1a2`) | generic-api-key | Google reCAPTCHA Enterprise **sample** — `6Le…` is a public **site key** used as `siteKey` |
| `.env.example:14` | generic-api-key | `VITE_RECAPTCHA_ENTERPRISE_SITE_KEY=6Le…` — public site key, `VITE_`-prefixed (intended client-exposed) |
| `.claude/claude.md:144` | generic-api-key | Same public site key in documentation |

Without a `.gitleaks.toml` allowlist, these false positives undermine the existing CI gitleaks gate (`.github/workflows/ci.yml`). **Recommendation:** add `.gitleaks.toml` allowlisting these paths/patterns so the gate stays green and meaningful.

> **History-rewrite decision:** per the audit plan, we do **not** rewrite git history. None of the 5 history hits is a real secret, so there is nothing to purge; rotation (F-2) is the correct remedy for the one chat-shared key.

## Verified-clean dimensions

### V-1 — SQL injection: N/A

No SQL database or raw SQL anywhere. No `pg`/`mysql`/`knex`/`sequelize`/`typeorm` dependencies; zero SQL keywords in source. The data layer is Firebase RTDB + Firestore (NoSQL). **SQLi is not an applicable attack class.**

### V-2 — XSS & NoSQL injection: clean

- **No dangerous sinks** in `frontend/src`: zero `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `document.write`, `insertAdjacentHTML`. All user content (guest names, wishes, RSVP) renders as React text children (auto-escaped).
- **Server-built HTML** (OG/WhatsApp preview tags, `backend/functions/src/digitalInvitePreview.ts`) routes every dynamic value through `escapeHtml()`.
- **NoSQL paths** are built from regex-validated tokens (`TOKEN_HEX_RE`, `/^[a-f0-9]{32}$/`), Firebase-Auth UIDs, and whitelisted usernames (`isUsername`) — no user input flows raw into a DB path/query. Firestore `where()` clauses use hardcoded fields/operators.
- **Input validation** is manual but thorough (`backend/functions/src/api/routes/digital/sanitize.ts`, `helpers.ts` — `isUsername`, `isE164`, `isRole`, length caps).

### V-3 — Authentication & crypto: strong

- **Token verification:** Firebase Admin `getAuth().verifyIdToken(token, true)` (revocation-checked) in `backend/functions/src/api/middleware/auth.ts`; no `jwt.decode()`-without-verify anywhere.
- **Passwords:** delegated to Firebase Auth — no custom hashing, no MD5/SHA1, no plaintext storage. Strong shared password policy with frontend/backend parity tests.
- **Optional RSA layer** (`passwordCrypto.ts`): RSA-2048 **OAEP-SHA256** (not PKCS1v1.5), correct envelope handling, documented threat model.
- **Crypto primitives:** tokens use `randomBytes`/`randomInt` (never `Math.random`); HMAC verification uses `timingSafeEqual`; no `crypto.createCipher`, no static IVs.
- **Authorization:** `assertAdmin()` + role middleware on Functions; RTDB/Storage/Firestore rules are **default-deny** with no `".read": true`/`".write": true`; Storage gated on `assignedGrooms` custom claim.
