# Security Re-Audit — 2026-07-02

Fresh, trust-nothing security re-audit of the **entire** Dawa codebase — backend
Express API + standalone Cloud Functions, Firebase RTDB/Firestore/Storage rules,
React frontend, Capacitor mobile app (`app/`), and the Python/Locust load-test
suite — plus the uncommitted paid-signup code no prior audit had seen
(`payments.ts`, `api/index.ts`, the `paid-signup-*` e2e specs).

Prior passes: [2026-06-11 hardening](../../wiki/Security-Model.md),
[2026-06-29 AI-vuln audit](./audit-2026-06-29.md),
[2026-07-01 backend hardening](../SECURITY_AUDIT.md). The backend was already
strong; this pass re-verified it end-to-end and extended coverage to the
under-audited surfaces.

## Method

- **Automated scanners** (baseline, working tree + full history):
  - **Semgrep 1.168** (OWASP + JS/TS + secrets), 353 files → **0 findings**.
  - **gitleaks 8.30** over **681 commits** + working tree → **0 real leaks**
    (1 history hit was a doc quoting the fake `bm90LWEta2V5` = "not-a-key" test

  - **npm audit**: functions **0**, frontend **21** (1 crit / 2 high / 18 mod) —
    all transitive via pinned `aws-amplify` (finding F-1, not reachable).

- Note: the **service-account key is NOT at the repo root** (TASK-008 appears
  already resolved) — `*-adminsdk-*.json` / `*-service-account*.json` are covered
  by three `.gitignore` rules and were never committed.

## Confirmed findings & fixes

Legend: severity is the **adversarially-corrected** value (several finder
severities were inflated and downgraded on verification).

### MEDIUM

**M1 — Firestore parent-doc public read leaked legacy design PII.**
`firestore.rules` granted `allow read: if true` on `digitalInvitations/{groomUid}`.
For legacy (pre-v2) grooms whose design was never deleted from the parent doc, a
direct Firestore read returned the full design payload (brideName, venue,
giftIban, story, …) plus design-workflow metadata — bypassing the REST endpoint's
`PUBLIC_DESIGN_FIELDS` allowlist, approved-only gate, and freeze gate. Groom uids
travel in guest invite links, so the doc id is discoverable.
**Fix:** parent-doc read is now owner/admin only (`firestore.rules`). Guests still
read via the server-mediated `GET /digital/:uid/public`. The `photographerFiles`
child rule uses a rule-internal `get()` (unaffected). The frontend has no Firebase
SDK, so no client read breaks. Rules test updated + expanded.

**M2 — Targeted account-lockout DoS on login.**
`auth.ts` checked the per-account failure counter and returned `429` **before**
verifying the password, so ~10 wrong-password POSTs from one IP (well under the
50/hr per-IP cap) locked a victim — including **admin** — out for up to an hour;
the counter clears only on a successful login the victim can no longer perform.
This is exactly the account-block that `autoBlock.ts` deliberately refuses to do.
**Fix:** the counter is now a *signal*, not a pre-credential block. The password
is always verified first — a correct password logs in and clears the counter (so
a legitimate user can never be locked out by someone else's failures); only a
*failed* attempt against an already-maxed account gets `429`. Brute force stays
bounded by the per-IP limiter + the `auth_failure` IP auto-block.

### HIGH

**H1 — Production credentials committed in the load-test suite.**
The literal admin/groom passwords were baked into `loadtest/locustfile.py`,
`loadtest/dashboard/configstore.py`, `loadtest/.env.example`, `CONFIGURATION.md`,
and a test fixture — with `BASE_URL` defaulting to production. Anyone with repo
read access obtained working prod admin creds.
**Fix (code):** removed the literal password fallbacks (missing env → empty →
login fails loudly, never silently authenticates against prod); `BASE_URL`
default flipped to `http://localhost:5000` (opt into prod via `LOADTEST_BASE_URL`);
`.env.example` + `CONFIGURATION.md` scrubbed to placeholders; the test fixture
password replaced with a neutral value.
**User action required (cannot be done in code):** ① **rotate** the real
admin + groom passwords (assume `DawaAdmin20••`/`DawaGroom20••` compromised);
② provision dedicated load-test accounts on staging; ③ optionally purge the old
literals from git history (BFG/`git filter-repo`).

### LOW / INFO (hardening — all fixed)

- **L1 — Photographer upload accepted ANY content-type.** A groom could upload
  `text/html` or a script-bearing `image/svg+xml` to the public-read
  `photographerFiles` bucket → JS/phishing host on the Google Storage domain
  (cross-origin, so not app-session XSS). **Fix:** `isSafeMediaContentType`
  (image/video only, SVG rejected) added to `photographer.routes.ts`.
- **L2 — `image/svg+xml` passed the media upload allowlist.** Same class on
  `media.routes.ts` (the `image/` prefix matched SVG). **Fix:** switched to
  `isSafeMediaContentType`.
- **Propagation of L1/L2 → storage rules:** the public-read `digitalMedia` and
  `photographerFiles` buckets now also require `(image|video)/*` and **reject SVG**
  at the rules layer (defense-in-depth for any direct client write; Admin-SDK
  backend uploads bypass rules). New storage-rules tests cover this.
- **L3 — Missing rate limiters.** Digital media + photographer **uploads**
  (50/200 MB) and all **gallery** read/curation routes + **`PATCH /settings`**
  had no limiter. **Fix:** per-uid limiters added (`MEDIA_UPLOAD_PER_USER`,
  `PHOTOG_UPLOAD_PER_USER`, `GALLERY_READ/WRITE_PER_USER`, `SETTINGS_PATCH_PER_ADMIN`).
- **L4 — `PATCH /digital/:uid/gallery` wrote `title`/`coverPhoto` verbatim.**
  **Fix:** bounded type/size validation (`boundedConfigField`), rejecting
  arrays/numbers/oversized blobs while preserving the client's localized-title /
  `{url,box}` shapes.
- **L5 — OG-image endpoint cached renders for non-existent tokens.**
  `/og/<random-hex>.jpg` rendered + **wrote** junk JPEGs to `og-cache/*`
  (Storage/write-op amplification). **Fix:** `renderAndCacheOgForToken` now only
  persists when the invite token actually exists (the pre-mint trigger path is
  unaffected). An IP limiter was deliberately **not** added — `/og/**` is hit by
  Meta/WhatsApp's few crawler IPs, so IP-throttling would break link previews;
  `maxInstances:10` already caps compute.
- **L6 (hardening) — login/OTP input bounds.** `POST /auth/login` and
  `/auth/send-otp` now reject over-length `username`/`password`/`phone`/
  `recaptchaToken` (large-body / ReDoS hygiene).
- **L7 (hardening) — API security headers.** `api/index.ts` now sends
  `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`, and disables `x-powered-by`.
- **L8 (hardening) — WhatsApp webhook verify-token.** `hub.verify_token` is now
  compared with `crypto.timingSafeEqual` (matches the signature check).

## Refuted (verified false positives — no change)

- **Admin-SDK key at repo root** — no key in the tree; caught by 3 `.gitignore`
  rules; never committed. Only crumb: a plaintext reset password in a committed
  allowlist string (`.claude/settings.local.json`), a minor hygiene item.
- **Refresh token in `localStorage`** — the standard Firebase web-auth model;
  no live XSS sink exists (only `dangerouslySetInnerHTML` is a hardcoded SVG),
  tokens are server-revocable.
- **Mobile WebView wildcard `originWhitelist`** — no reachable navigation sink;
  the screen loads one fixed same-origin URL rendering the groom's own draft.
- **WhatsApp verify-token `===`** — not reachable (echoes only the challenge;
  POSTs use constant-time HMAC). Hardened anyway (L8).
