# Architecture Decisions

Index of the closed architectural questions in [[Dawa]] (full rationale in `DECISIONS.md`). Each exists so future engineers don't re-litigate them.

- **No Firebase Auth SDK on the frontend** — REST auth + custom token manager. See [[Authentication]], [[REST API Architecture]].
- **REST API layer instead of direct RTDB/Firestore SDK** — server owns authorization. See [[REST API Architecture]].
- **Polling instead of realtime** (except live GPS via SSE). See [[Polling and Realtime]].
- **RTDB sharded by groomUid** — rules apply to subscribed path. See [[Data Storage Model]].
- **Synthetic email auth** (`username@dawa.local`) — users have no email. See [[Authentication]].
- **JWT custom claims for role + assignment** — unified `role` string replaced legacy `admin: true`. See [[Authentication]], [[Security Model]].
- **Firestore for digital invitations** — RTDB had write-after-login rollback. See [[Digital Invitations]].
- **Inline styles only** — see [[Inline Styling Convention]].
- **No App Check** — rate limiting is the abuse gate instead. See [[Security Model]].
- **Rate limiting: in-memory, per-instance** — resets on cold start; acceptable for low-volume endpoints. See [[Security Model]].
- **Phone OTP password reset** — no email reset links. See [[Authentication]].
- **Server-side face index (not client-only or third-party)** — a Cloud Function indexes every photographer photo's faces once; guests enrol a descriptor server-side for an instant, uncapped gallery. Runtime is `@vladmandic/face-api` on the **tfjs WASM backend** (not tfjs-node — no native binary build risk; speed irrelevant for a background trigger), with the recognition weights kept **byte-identical** to the browser copy so client/server descriptors stay comparable. See [[Face Matching]].
- **Groom mobile app = Expo / React Native** (REVERSED from Capacitor on 2026-06-26, one day after the Capacitor decision), separate `app/` package. The reversal: the user made *genuinely native, smooth UX* a non-negotiable product standard, accepted regardless of measurement. Fully-native (Swift/Kotlin) was rejected because the only thing that would justify it — heavy AR/3D — is the **guest-facing** invitation experience (guests tap a WhatsApp link, they don't install the app), so the groom *management* app has zero native-only requirement. Expo wins here: reuses the DOM-free JS logic, same React model, **EAS builds iOS in the cloud** (dev is on Windows, no Mac), and runs the existing Three.js 3D via `expo-gl`. Business logic now lives in a DOM-free **`@dawa/core`** package: the web imports it via a Vite alias + one-line re-export shims (kept 192 import sites untouched), the Expo app via Metro `extraNodeModules` — **no npm workspace** (avoids disturbing the Firebase Functions deploy + the Windows npm workaround). Platform edges are injected through adapters (storage → `expo-secure-store`, env → `expo-constants`). iOS payments still **Apple StoreKit IAP**, Android **Lemon Squeezy**. Decided 2026-06-26; Phases 0–2 built same day. See [[Mobile App]].
- **Premium 3D invitation envelope rebuilt INSIDE the shared celestial scene** (not a second WebGL canvas/context) — one renderer; the matte-cardstock + wax-seal + cream-card reveal floats in the particle starfield and dissolves straight into it. PBR materials + ACES tone-mapping + AA are enabled on the shared renderer **only when an envelope is present** (the particle `ShaderMaterial` is pinned `toneMapped:false`, so non-envelope pages stay byte-identical). Responsibility split: `envelopeMesh.js` owns geometry/materials/bursts + a returned camera POSE; `celestialEngine.js` owns the clock + camera + glide. Gated to device **tier ≥ 2** (tier-1/no-WebGL/reduced-motion get the 2D fallback). Theme drives a full per-theme envelope palette (`themeToEnvelopePalette`) with contrast clamps. Decided + built 2026-06-26. See [[Digital Invitations]].
- **`blessing` + `welcome` are new authorable `{ar,he}` design fields scoped to the envelope card** (3D + 2D fallback, not the hero/sections) — added through the strict backend allowlist (`sanitize.ts` `localizedScalars` + `DESIGN_FIELDS`); they flow onto invite tokens via the existing `...designFields` snapshot spread (no snapshot-builder change). See [[Digital Invitations]].
- **Groom app on Expo SDK 56 + `pnpm-workspace.yaml` as a Metro server-root marker** (upgraded from SDK 52 on 2026-06-28, commit `0d56fc7`). The version bumps (React 18→19, RN 0.76→0.85, New Architecture now mandatory) were routine; the real blocker was that **Metro 0.84 only bundles files under its *server root*, which Expo derives from `getMetroServerRoot()`**. With no workspace declared the server root collapses to `app/`, so the sibling `shared/` (`@dawa/core`) tree can't be indexed ("Failed to get the SHA-1 … not watched"). Resolution: a repo-root **`pnpm-workspace.yaml`** (`packages: [app, shared]`) — `resolve-workspace-root` reads it, flips the server root to the repo root, and adds `shared/` to watchFolders (the standard Expo monorepo wiring). **This does NOT contradict the "no npm workspace" decision above: npm ignores `pnpm-workspace.yaml` entirely** (the repo still installs per-package via `--prefix`), so the Firebase deploy and Windows npm workaround are untouched — only Expo's Metro reads it. `@dawa/core` is then resolved by a `metro.config.js` `resolveRequest` mapping the bare specifier to absolute `shared/src/*` paths (its `package.json` `exports` map doesn't line up with a plain alias). See [[Mobile App]].
- **3D celestial envelope is WebGL-only; no 2D fallback** (2026-06-29) — the immersive intro envelope + particle world render via three.js (`components/digital/celestial/`), gated by `useDeviceCapability`. Policy now leans INTO the 3D: only an explicit **reduced-motion / data-saver opt-in, or no WebGL at all** drops to tier 0 (CSS ambience floor + **no envelope at all**). Software GPUs and in-app browsers (incl. FB/Instagram) still **attempt** the 3D at the lowest quality tier, with the runtime FPS guard as the safety net. The old 2D wax-seal `EnvelopeIntro` fallback was **deleted**. This fixed software-WebGL desktops being shunted to a worse 2D intro. The same shared gate also drives the landing-page hero backdrop. Accepted trade-off: hard in-app browsers can occasionally mis-render WebGL with no auto visual-glitch detection. See [[Digital Invitations]], [[Visual Design System]].
- **Luxury PBR envelope restored over the flat interim build** (2026-06-29) — the celestial intro envelope is the full PBR build (`MeshStandard`/`MeshPhysical`, lights as group children, equirectangular studio env-map, ACES tone-mapping, gold-foil arabesque flap, satin lining, glossy wax seal, baked bilingual calligraphy card), restored from the merged `feat/arch-tech-debt-seams` work (`2f56adf`/`3a9345a`) after an interim commit (`eb3ca55`) had stripped it to flat `MeshBasicMaterial`. It renders **full PBR on every WebGL-capable device and is never downgraded during the reveal** (`celestialEngine.js` skips the FPS guard while `mode !== "scroll"`). Accepted trade-off: weak phones may stutter — no auto-fallback for the envelope itself; the particle field keeps its FPS safety net only after hand-off. Recoloured **white-default + theme-aware** (`utils/themeToEnvelopePalette.js`) with **foil pinned to metallic gold on every theme**; the card bakes the couple names (so the DOM couple-names reveal was dropped) and the centre satin ribbon was removed. See [[Digital Invitations]], [[Visual Design System]].
- **Comprehensive test harness: hybrid specs + crawler, emulator + prod-smoke** (2026-06-29) — a multi-layer harness (`npm run test:full`): exhaustive feature specs + 7 cross-role journeys + an auto-crawler + visual regression + i18n/a11y sweeps + REST API route tests (closes TASK-006), feeding ONE consolidated report (`test-report/`) + deduped auto-filed GitHub issues. Full destructive run vs the **local emulator**; separate **read-only prod smoke** (`@prodsafe`). External boundaries (WhatsApp, Lemon Squeezy, GPS, camera, face-match) **stubbed at the boundary**. CI per-PR gate is sharded (Chromium+WebKit, `@visual` excluded); visual advisory until linux baselines exist; crawler report-only by default (`CRAWLER_STRICT=1` to gate). Trade-offs: visual scoped to deterministic screens (animated/3D pages can't stabilize); full local run is resource-heavy. See [[Comprehensive-Test-Harness]].
- **Physical track gated OFF at compile time (`FEATURES.physical=false`)** (surfaced 2026-06-29) — handwritten/driver/proof/GPS track is beta, disabled for everyone; the **digital** track is live. Tests are flag-aware: physical UI specs skip unless `TEST_PHYSICAL=1`; the physical backend is still covered via the API. See [[Comprehensive-Test-Harness]].
- **Central `--inv-*` spacing tokens for the digital invite** (2026-06-30) — the public invitation's cross-cutting vertical spacing (section padding, section-head gap, footer bottom) lives in CSS custom properties on `.dawa-inv` (`--inv-sec-pad`/`--inv-head-gap`/`--inv-foot-bottom`), not scattered literals, so density is a one-knob change. `--inv-sec-pad` is a `clamp(30px,5vw,48px)` — fluid, so the rhythm auto-shrinks on phones. This is a scoped exception to the otherwise token-less, per-component spacing; introduced in the round-two tightening pass. See [[Digital-Invitations]], [[Visual-Design-System]], [[Inline-Styling-Convention]].
- **Emulator seeds the namespace the Functions read** (2026-06-29) — `seed-emulator.cjs` writes RTDB namespace `dawa-aa793` (the legacy default the emulator `FIREBASE_CONFIG` advertises), not `dawa-aa793-default-rtdb`, so seeded data is visible to the Functions (the app touches RTDB only via the Admin SDK, so namespace = data location only). Fixed previously-empty seeded reads incl. existing e2e. See [[Data-Storage-Model]], [[Comprehensive-Test-Harness]].
- **Controlled soft launch + DPIA-grade biometric consent** (2026-06-30) — first public exposure is a **controlled soft launch**: invite-only, the operator manually onboards 1–5 real grooms, **payments off** (Lemon Squeezy stays unconfigured). That lowers the bar (captcha deferred; Sentry to be turned on) but biometric face data is handled **full DPIA-grade**, not notice-only. Core pattern: **face indexing is gated behind a per-wedding consent flag** (`indexingConsentGate`, opened only when the groom publishes WITH an explicit acknowledgment that guests were notified) — until then `faceIndex/trigger.ts` defers indexing with no AWS call; weddings published before the gate existed keep working. Active users (selfie search, gallery viewers) give affirmative checkbox consent; passive subjects (everyone auto-indexed in photographer photos) are covered by the groom ack + a notice + a fast-follow self-service opt-out (admin manual-erase is the interim backstop). Grilled, built, browser-verified 2026-06-30. The concurrent demo-invitation feature in the same tree was left uncommitted. See [[Face Matching]], [[Digital Invitations]], [[Security Model]].
- **Per-design custom background for the digital invite** (2026-06-30) — guests can now get a fully groom-designed 2D backdrop instead of the 3D celestial world, gated per design by a **"Use my background"** toggle (`background.enabled`). When on, the invite shows the custom backdrop (solid/gradient fill OR fixed cover image + dim overlay, plus edge-only decorative circles + petals/sparkles) to ALL guests; the WebGL envelope intro still plays then **fades out** to reveal it. Stored as one flat `background` override object (mirrors `envelope`) on the design doc; reaches guests via `DESIGN_FIELDS`→`PUBLIC_DESIGN_FIELDS`. The image is **server-managed** (upload route `target=background`, deep-merged onto `background.image`) and **stripped from client PATCH** (`sanitizeBackground`), so clients can't inject arbitrary background URLs. Circles use **`cqmin` (container-relative) sizing with a `vmin` fallback** and are **centred exactly on each edge point** so the screen centre stays clear at any size ("nothing in the centre, seen on the edges"). Grilled (9 decisions), built, browser-verified. See [[Digital-Invitations]].
- **App renders the digital invitation via a WebView, not a native port** (2026-07-01) — the mobile design page's "use device hardware to render the invitation" is met by loading the **existing web renderer** in a `react-native-webview`, whose WebGL 3D envelope runs on the **device GPU**. One renderer, zero fork, always identical to what guests see — chosen over an expo-gl/react-three-fiber native re-implementation (a permanent second renderer that would drift). Drafts aren't public, so the WebView loads a **new authenticated groom-facing route `/preview/digital/:designId`** (`DigitalDesignPreviewPage`) that reads the owner's draft; the app seeds the WebView's `localStorage` with the groom's tokens (`tokenManager.peekTokens()`) before content loads. The **editor itself is a native full-parity form** (`app/(groom)/design.jsx` + `useDesignEditor`) autosaving through `patchDesignById`; the preview shows the saved draft (the accepted lag of the authenticated-URL feed over postMessage). Field lists are unified in `@dawa/core/data/digitalDesignSchema.js`, imported by BOTH editors. Camera capture reuses `expo-image-picker` `launchCameraAsync` (no `expo-camera`); contact import reuses `expo-file-system` `File.pickFileAsync` (no `expo-document-picker`). See [[Mobile-App]], [[Digital-Invitations]].
- **i18n misses render the raw key (fix + guard)** (2026-07-01) — `makeT` resolves `STRINGS[lang][k] || STRINGS.ar[k] || k`, so a key **absent** from the registry returns the literal key string, which is truthy and defeats the ubiquitous `t(k) || "arabic fallback"` pattern → English-looking keys on screen (hit the app's login + groom pages). Rule: **every `t()` key must exist in ar AND he**; enforced by a new unit guard (`appKeyCoverage.test.js`) that scans `app/` and fails on any missing key. See [[Mobile-App]].
- **Bulk guest edits go through ONE batched endpoint, not N calls** (2026-07-01) — the app's bulk role change sends a single `PATCH /digital/:uid/guests` with `{ updates: [{ id, ranks }] }`; the server commits a **Firestore WriteBatch chunked at 500 ops** (`guestStore.patchMany` over the existing `FirestorePort.batchWrite`), so a bulk edit is one HTTP call + a handful of atomic commits regardless of guest count (the "don't overload the server" requirement). The client pre-computes each guest's final ranks (Add = union, Replace = the set); the route is **ranks-only** (reuses `coerceRanks`), owner/admin-gated, capped at 1000 updates. No schema/rules change — guests already carry `ranks` and writes use the Admin SDK. Also: the app's Add-Guest **contact import switched from `.vcf/.csv` file pick to native `expo-contacts`** (permission-gated multi-select), reusing the same bulk-add pipeline. See [[Mobile-App]].
